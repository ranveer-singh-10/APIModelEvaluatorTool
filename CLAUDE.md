# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A Python sandbox for experimenting with the Anthropic Messages API (`AnthropicAPI.py`) and the OpenAI Responses API (`OpenAIAPI.py`), and for comparing what each model's calls cost and how accurate they are (`evaluation.py`).

## Environment

- Python 3.13, virtualenv in `.venv/` (PyCharm-managed). No `requirements.txt`; dependencies are `anthropic`, `openai` and `python-dotenv`, plus `nbstripout` for the notebook.
- `.gitattributes` runs notebooks through the `nbstripout` git filter, so outputs and execution metadata are stripped when a notebook is committed (the working copy keeps them). The filter itself lives in `.git/config`, so a fresh clone needs `.venv/Scripts/nbstripout --install --attributes .gitattributes` once; until then, git silently commits notebooks with their outputs. Once installed, the filter is required, so a notebook commit fails if `.venv` is missing.
- `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` are loaded from `.env` via `load_dotenv()` at import time. `.claude/settings.json` denies reading `.env` — don't try to open it.
- There are no tests, linter config, or build step.

## Running

```
.venv/Scripts/python AnthropicAPI.py
.venv/Scripts/python OpenAIAPI.py
.venv/Scripts/python evaluation.py
```

None of the files has a `main`; experiments are the `tester*` / `structured_data_tester` / `evaluate*` / `chat_ui` calls, invoked by uncommenting a call at the bottom of the file. `notebook/eval_testing.ipynb` does `from evaluation import *`; its `evaluate*` cells are commented out the same way, so Run All makes no API calls. Every run makes real (billed) API calls.

## Architecture

### Provider modules

`AnthropicAPI.py` and `OpenAIAPI.py` each expose the same interface, which `evaluation.py` relies on: `MODEL_PRICING`, `chat(messages, model=, system=, stream=, return_full_response=, return_usage=)`, `text_from_response(response)`, `stop_reason(response)`, `usage_summary()` returning the same keys, and `user_content(text, attachments)`. `user_content` turns provider-neutral attachments (`{"type": "image" | "pdf" | "text", "name", "media_type", "data"}`, with base64 data for images and PDFs and plain text for text files) into that provider's content blocks: Claude `image` / `document` blocks, or OpenAI `input_image` / `input_file` / `input_text` parts. An attachment may also carry `"cache": True`: Claude puts a prompt-cache breakpoint (`cache_control`) on its block, and OpenAI ignores it because it caches repeated prompt prefixes automatically. Keep that interface in step when changing either module, and keep provider-specific code out of `evaluation.py`.

### AnthropicAPI.py

- A module-level `client = Anthropic()` is shared by all helpers.
- `chat()` is the central entry point; everything new should go through it rather than the legacy `make_request` / `chat_old`. It builds a `params` dict and optionally adds `system`, `output_config` (structured JSON output), and `tools` (with `fine_grained=True` adding `eager_input_streaming` to custom tools). The `temperature` argument is accepted but never sent: the installed SDK uses API version 2026-10-21, which rejects sampling parameters with a 400.
  - Defaults: `model="claude-haiku-5-5"`, `stream=True`, `max_tokens=4000`.
  - Returns concatenated text blocks, or the full `Message` when `return_full_response=True` (needed for tool use and web search). With `return_usage=True` it returns `(result, usage_summary)` instead.
- Cost estimation: `MODEL_PRICING` (USD per million tokens, hand-maintained, plus `LONG_CONTEXT_PRICING` for Haiku 5.5 above 100K prompt tokens) feeds `estimate_cost(model, usage)`. It charges cache writes at 1.25× input (5-minute TTL) or 2× (1-hour TTL), and returns `None` for models not in the table. `usage_summary()` combines the token counts and cost. When adding a model, add its prices to `MODEL_PRICING`.
- Conversation history is a plain list of dicts built with `add_user_message` / `add_assistant_message`. The `_multi` variants accept a full `Message` and copy its `content` blocks — use these in tool-use loops so `tool_use` blocks are preserved.
- `build_tooluse_json` builds a `tool_result` payload but takes the ID from `content[0]`, which is wrong when Claude emits text before the tool call.
- Streaming: `chat()` goes through the stream's events once, printing text and tool-input chunks as they arrive. Don't add a second loop such as `text_stream`: the first loop uses up the stream.

### OpenAIAPI.py

- A module-level `client = OpenAI()`. `chat()` mirrors the Anthropic one on the Responses API: `system` is sent as `instructions`, an Anthropic-style `output_config` becomes `text={"format": ...}` (with `name` and `strict` added), and `max_tokens` becomes `max_output_tokens`. `temperature` is accepted but not sent. Default model is `gpt-6-luna`. Streaming goes through the events once, printing `response.output_text.delta` and function-call argument chunks.
- `stop_reason()` returns `status`, or `incomplete_details.reason` (e.g. `max_output_tokens`) for an incomplete response.
- Usage: OpenAI's `input_tokens` includes cached tokens and cache writes. `usage_summary()` reports uncached input as `input_tokens` to match Anthropic, and adds `reasoning_tokens` (already counted in `output_tokens`, which is what's billed). `estimate_cost()` charges cache writes at 1.25× input (the 30-minute rate; 12-hour writes cost 2×, but the usage doesn't say which was used). `MODEL_PRICING` covers the GPT-6 family only, with standard-tier prices from OpenAI's pricing page, plus `LONG_CONTEXT_PRICING` for prompts above 272K tokens.
- Tool-use helpers: `add_response_output(messages, response)` appends every output item (reasoning, function calls) to the history; `build_tool_result(call_id, output)` builds a `function_call_output` item.

### evaluation.py

- `PROVIDERS` maps a provider name to its module. `provider_for(model)` finds the provider whose `MODEL_PRICING` contains the model, falling back to the `claude-` / `gpt-` / `o*` name prefix. `run_model()` makes one non-streaming call and returns the result dict that gets logged, which includes `provider`.
- `evaluate(model, request)` makes one non-streaming call through `chat()` and prints the response, token counts and estimated cost. `evaluate_all_models(prompt)` does the same for every priced model of every provider (or only `providers=[...]`, or an explicit `models=[...]`) and prints a comparison table. With `log=True`, both append to `logs/eval_log.json` (a JSON array of runs) via `log_evaluation()`.
- `run_model()` / `_run_model_safe()` take an optional `output_config` (Anthropic-style structured output, translated by each provider); the grader uses it.
- Scoring: every score is on one 1-5 scale, and `PASS_SCORE` (4) or more is a pass. `score_response(result, prompt, expected=, rubric=, scorer=, judge_model=)` adds `result["score"]` = `{value, scorer, reasoning, judge_model, judge_usage, error}`. Scorers (`SCORERS`): `llm_judge` (default) asks `JUDGE_MODEL` (`claude-sonnet-5-5`) for `{reasoning, score}` through `JUDGE_OUTPUT`, a JSON schema with `score` an enum of 1-5, with `JUDGE_SYSTEM` describing each level (it grades content only: working, markdown, notation and ignored format instructions such as "give only the final answer" never lower a score, while a requirement written in the rubric, like a word count, is graded in full) and the prompt, expected answer, rubric and response in separate tags; it needs an expected answer or a rubric. `exact` and `contains` compare against `expected` after `_normalise()` (case, whitespace and surrounding punctuation ignored) and record a pass as 5 and a fail as 1. A failed model call gets `score: None`, so it isn't counted as a wrong answer; a failed or unreadable grade keeps `value: None` with `error` set. The grader's tokens and cost live in `judge_usage`, never in the model's `usage`, and a scored entry's `judge_cost` (from `judge_cost()`) is kept apart from its `total_cost`.
- `evaluate()` and `evaluate_all_models()` take optional `expected=`, `rubric=`, `scorer=` and `judge_model=`. Scoring is on when `expected` or `rubric` is given (`_resolve_scorer`, default `llm_judge`); the table gains a Score column and the log entry records `expected`, `rubric`, `scorer`, `judge_model` and `judge_cost` (`_scoring_fields`; unset fields are left out).
- Batch mode: `evaluate_batch(cases, models=, providers=, system=, scorer="llm_judge", judge_model=, max_workers=8, confirm=True, log=False)`. `load_cases()` takes a list of `{prompt, expected?, rubric?, id?}` or a `.json` / `.jsonl` path (relative paths also tried from the project folder; `datasets/example.json` holds 11 easy-to-moderate cases and `datasets/hard.json` 15 harder ones, with every exact answer checked by code), checks each case and gives missing ids `case-N`. Every case is checked against the scorer before anything runs. It prints the number of billed calls (and grading calls) and asks `Run it? [y/N]` unless `confirm=False`. Every case x model pair runs in a thread pool and is scored in the same task. `_summarise_batch()` gives one row per model: cases, errors, scored, `avg_score`, `pass_rate`, `total_cost`, `avg_cost`, `cost_per_pass` (cost of the scored calls / passes, grading excluded) and `avg_seconds`. It returns `{batch_id, summary, results}` (each result carries `case_id`). With `log=True` it writes one `type: "batch"` entry per case (with `batch_id`, `case_id` and the scoring fields) in a single write under `_log_lock`, through `_make_entry()` / `_write_log()`, which `log_evaluation()` also uses. `scorer=None` runs a batch without scoring.
- `view_logs()` starts a local server on 127.0.0.1 (port 8765, or the next free one, printing why when it falls back). The server class `_LocalServer` binds exclusively on Windows (`SO_EXCLUSIVEADDRUSE`, with address reuse off): Python's default `SO_REUSEADDR` there lets two servers listen on one port, so a stale viewer in a notebook kernel, or any other local program, would share this server's requests, `/run` included. Keep it that way.
- `view_logs()` runs the server in a daemon thread and opens `web/log_viewer.html`, a self-contained page with no dependencies for filtering, charting and exporting the log. `chat_ui()` starts the same server (via `_ensure_server()`) and opens `web/chat.html`; from a script, pass `block=True` so the script doesn't exit and take the daemon server with it. The server answers only `GET /` (the log viewer), `/log.json` (the log file), `/chat` (the chat page) and `/models` (`default_models()` with their providers), plus `POST /run` and `POST /score`, and returns 404 for everything else, so it never exposes the project folder or `.env`. Keep it that way if you change it.
- Attachments: a message dict with an `attachments` list is converted per model by `_provider_messages()` (in `run_model()`) through the provider's `user_content`. `_check_attachments()` enforces the allowed types (PNG/JPEG/GIF/WebP images, PDFs, UTF-8 text sent as `text/plain`), valid base64, and `ATTACHMENT_MAX_BYTES` per file (5 MB image, 10 MB PDF, 1 MB text), and returns each file's `attachment_summary()` (name, type, media type, bytes), which callers add up and log without decoding the data again. `ATTACHMENTS_MAX_TOTAL_BYTES` (20 MB) applies to everything one request resends. The log records only those summaries, never the file data.
- Context files: files for the whole chat conversation, sent as `context_files` and checked the same way. `with_context_files()` puts them at the start of each model's first user message, ahead of that turn's own attachments, so every turn resends them. It marks the last one with `"cache"`, so Claude models pay the cache-read rate for them after the first turn. The system prompt can't hold them, because both APIs take only text there. They count toward the 20 MB total, and each logged turn records their `attachment_summary()` as `context_files`.
- Manual grading: `set_manual_score(entry_index, timestamp, model, value, note=None, log_file=)` grades one logged result 1-5 (`value=None` clears it). The entry is found by index and must still have that timestamp, and the run must have exactly one result for the model; otherwise it raises `LookupError` instead of grading the wrong result. A failed call can't be graded (`ValueError`), and notes are capped at `MANUAL_NOTE_MAX` (2000) characters. The grade is written as `score = {value, scorer: "manual", reasoning: <note>, judge_model: None, judge_usage: None, error: None, previous: <the score it replaced>}`. Grading again keeps the original automatic score in `previous`, and clearing restores it, or removes the `score` key when there was none. It reads, edits and writes the log under `_log_lock`. Entry-level fields (`total_cost`, `judge_cost`, `scorer`) are left alone.
- `POST /score` takes `{entry, timestamp, model, value, note}` and calls `set_manual_score`. It answers 409 for `LookupError` (the page then reloads the log), 400 for bad input and 500 if the log can't be written, and otherwise returns `{result}`. It makes no API calls. Like `/run`, it only accepts requests that `_from_own_page()` allows; its body limit is `max_score_body_bytes` (100 KB).
- `POST /run` takes `{prompt, system, models, log, session_id, histories, files, attachments, context_files}` and makes billed calls. It is refused (403) unless `Host` and `Origin` are the server's own 127.0.0.1/localhost address and the body is JSON (`_from_own_page()`, shared with `/score`), so other websites open in the browser can't trigger calls. It only accepts models from `default_models()`. `histories` (optional) maps each model to its own conversation so far, as messages alternating `user`/`assistant` (checked by `_check_history`). A user turn refers to its attachments by id in `attachment_ids`, and `files` maps each id to the attachment, so a file in several models' histories is sent once and the body stays within `max_body_bytes` (40 MB). Unknown ids and files no history uses are refused. A user turn may be attachments with no text. With context files, the first turn may have no text at all (a context-only turn), but only while no model has any history yet. The server keeps no state: each model is sent its history plus the new prompt. It runs the models in parallel through `_run_model_safe()` (the error-to-result wrapper `evaluate_all_models` also uses) and sends back one NDJSON line per model as each finishes, then a `done` line. Unless `log` is false it logs one entry per turn with `type: "chat"`, under `_log_lock`. With a `session_id`, `log_evaluation()` also records `session_id`, `turn` and `session_total_cost` (this turn's `total_cost` plus that of the session's earlier logged turns), and the `done` line returns `turn` and `session_total_cost`.
- `web/chat.html` has a checkbox for every priced model (all checked by default), a prompt box with an optional system prompt, and one tab per model holding that model's whole conversation, with each call's tokens and cost and the model's session cost. The page holds the conversation: each model keeps its own history, and a failed or empty reply is left out of it. The models, system prompt and Log checkbox are locked after the first send until **Clear conversation** starts a new session. A turn the server refused (nothing billed) is taken back. Each conversation gets an 8-character session id, shown in the summary line with a copy button and a **View in log** link to `/?session=<id>`. Files can be attached with the **Attach files** button, by dropping them on the prompt box or by pasting images. The page applies the same type and size limits as the server before sending. Attachments become part of each model's history (by id, with the files kept in `session.files`) and are resent every turn. Send is disabled ("Loading files…") while any file is still being read, so a file can't miss the turn it was added for. A collapsible **Context files** area (with its own button and drop zone) holds files for the whole conversation. The page keeps them separately from the history, and they lock with the models and system prompt. Clear conversation keeps them for the next conversation.
- Both pages explain their controls with tooltips: any element with a `data-tip` attribute shows that text in a bubble on hover or keyboard focus, and section headings have a focusable ⓘ (`.info`) button. Each page carries its own copy of the small tooltip script and styles. Give new controls a `data-tip`, and keep the text in step when a control's behaviour changes.
- `web/log_viewer.html` has a **Chat session** filter listing the sessions in the log (id, start time, turns, first prompt). It reads `?session=<id>` on load and keeps it in the address bar. A chat turn's run card shows its session id, turn and session total so far, with a link to filter to that session. Run cards list a turn's attachments and context files. The search box matches session ids and their file names, and the CSV export has `session_id`, `turn`, `session_total_cost`, `attachments` and `context_files` columns. The page can also open a log file directly, without the server. It groups results by model, filters by provider (the dropdown lists the providers in the log, and the model checkboxes show only the selected provider's models; entries logged before `provider` was recorded take it from another result for the same model, or else from the model name, using a copy of `provider_for`'s prefix fallback in `inferProvider`), and treats both `end_turn` and `completed` as normal stops.
- Scores in `web/log_viewer.html`: `scoreFields()` reads each result's `score`, and the page's `SCORE_MAX` / `PASS_SCORE` copy the Python constants, so keep them in step. Once any matching call is scored, the tiles add Avg score, Pass rate and Grader spend, the Models table adds Avg score, Pass rate and Cost per pass (columns marked `score: true`, hidden otherwise), and the charts add **Accuracy vs cost** (`scatterChart`: one dot per model, average score against the average cost of its scored calls, with a log x-axis when costs differ 10-fold or more, a dashed pass line, and name labels dropped where they would overlap) and an Average score bar chart. A **Batch** filter (`renderBatchFilter`, `setBatchFilter`) lists the batches in the log; batch run cards show the batch and case id, the expected answer and rubric, an average score badge, and each result's score badge and grader reasoning and cost. Search also matches batch and case ids, expected answers, rubrics and grader reasoning, and the CSV export adds `batch_id`, `case_id`, `expected`, `rubric`, `score`, `scorer`, `judge_model`, `judge_cost`, `score_reasoning` and `score_error`.
- Manual grading in `web/log_viewer.html`: every successful result card has 1-5 buttons, a note box and, once graded, **Clear my grade** (`gradingControls`). A click saves at once through `saveGrade()` → `POST /score`, sending the entry index, its exact logged timestamp (`rawTimestamp`) and the model. The page then swaps the returned result into `state.entries` and rebuilds the rows with `loadEntries(..., keepView=true)`, so open cards stay open; a 409 reloads the log. The controls are disabled (with the reason in a tooltip) unless the log was served by the server (`state.fromServer`). `scoreFields()` reads a manual grade as the result's `score` (so it counts in every total), exposes the replaced grader score as `graderScore` / `graderReasoning`, and still counts that grader's cost in Grader spend. Cards show "You: n/5", a "grader n/5" badge (red when the two differ by `DISAGREE_BY` (2) or more), your note and the grader's reasoning. A **Scoring** filter offers Unscored, Manually graded and Grader disagrees. The CSV export adds `manual_score`, `grader_score` and `manual_note`.

## Workflow for any feature or task
1. **Explore**: read the relevant files first. Don't edit anything yet.
2. **Plan**: write a short numbered plan (files to change, approach, tests).
   Then STOP and wait for my approval.
3. **Code**: only after I approve.
4. **Commit**: suggest a commit message and wait. Don't run git commit
   yourself.
